Documenting Intent: The Why Agents Can't Read From Code

Decision-making is the real bottleneck in the AI SDLC. Here's how we capture the why behind the code with glossaries and ADRs, without drowning in docs

Published Sun, Nov 22, 2026 by Yarel Maman

In my SDLC today, most of my time in the execution phase goes to making decisions and applying judgment. In practice, that’s my main bottleneck. 🧭

All of these decisions fall under one umbrella: Intent. The decisions, conclusions and thoughts that come from me and from the process.

To make development more efficient, my goal is to cut down how often I need to step in and steer the ship, without hurting quality. If I let the agents run free, I’ll quickly end up with a bloated system that both they and I struggle to understand.

As the engineer in the loop, my value is intuition, judgment and business context. Claude can be an excellent programmer, but without the context of the business, the architecture and what we’ve seen in production, the risk goes up and I turn into its babysitter.

The challenge here is managing knowledge that moves fast, when the old tools no longer work.

The Old Habits Trap

Like many others, I tried building a background process where Claude documents changes and maintains design docs for both people and agents. Pretty quickly it did more harm than good:

  • Drift. The docs became a view of the code, and soon the code said one thing while the doc said another.
  • Implementation details leaked in. Code and implementation details crept into the docs, which made the drift even worse.

The docs lost their credibility and the idea was abandoned. But something was still missing.

Why Code Alone Isn’t Enough

Code tells you how the system works. It doesn’t tell you why:

  • Was this solution built after an experiment on 1,000 cases, or as a band-aid for a production bug?
  • Was it a deliberate decision by a developer, or did an agent just make an assumption?

Beyond that, today’s systems aren’t just code anymore. Agentic systems are a good example: the code is tied to prompts and harnesses that evolved through evals and lessons learned in production. Where is that documented? Certainly not in the code. A week from now, another developer (or me) might make a breaking, out-of-context decision, and I’m back to babysitting.

The Fix: Separate the “How” From the “Why”

Design docs have two parts: how it works, and why we chose X over Y. The first part no longer needs documenting, since models are great at reading code and explaining its logic. The second part is the Intent, and agents can’t read our minds.

There’s a lot of hype around the “Company Brain”, but garbage in, garbage out applies here too: the more inaccurate or unnecessary information we flood agents with, the worse the results. The trick is knowing what’s worth documenting.

What We’re Trying Right Now

The approach we’ve been running for a while is built on lean tools that live in the repo:

  • 📖 Glossary: a short dictionary of our domain terms. It maps parts of the system to their product definitions and gives everyone a shared language.
  • 📌 ADRs (Architectural Decision Records): short files that capture an architectural decision during planning and execution. Every decision sits on a timeline, and when a new decision replaces an old one, we mark or update the old one.
  • 🏷️ Index and tags: each ADR is tagged, so agents can pull only the decisions relevant to the area of code they’re working in. We built a script that, given an area of the code, points to the ADRs that cover it.

The goal is to capture the hidden technical intent without burying ourselves in paperwork. Before every change, the agents explore and learn the story behind the code.

Just like I trust a developer who’s been on the team for a year more than a new hire, these steps let me give agents more autonomy.
